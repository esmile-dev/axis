# 方法论：Vibe Coding 全栈开发工作流

## 四阶段核心流程

### 1. 诊断期：收集与发现需求
- **从痛点出发**：从日常工作/生活中寻找真实的痛点，例如“烦躁/被打断/重复劳动/记不住的点”。
- **区分优先级**：严格区分“痛点”（Must-have，核心解决的问题）和“痒点”（Nice-to-have，锦上添花的功能）。

### 2. 收敛期：划定边界与架构选型
- **领域视角（DDD）**：用领域驱动设计的视角来梳理业务实体和关系。
- **梳理核心图表**：绘制核心框架图、数据流程图、状态流转图等，为 AI 提供全局上下文。
- **确定技术栈基准线**：**Vibe Coding 强烈建议选择 AI 训练数据丰富、生态成熟、有严格强类型支持的技术栈**（例如：Next.js + TypeScript + TailwindCSS + Prisma + Postgres）。
- **MVP 原则**：避免做“大而全”，必须列出明确的"**不做的事情（Non-Goals）**"清单。

### 3. 设计期：编写面向 AI 的 PRD
- **Jobs-To-Be-Done (JTBD) 框架**：不要简单罗列"功能列表"，而是描述"雇佣这个软件帮你完成什么任务"。
  - **格式：**`当 [特定场景] 时，我想要 [采取的具体行动]，以便于 [获得什么预期效果]。`
- **明确边界**：定义严格的验收标准和"完成的定义" (DoD - Definition of Done)。
- **提供示例**：如果不确定 UI 长什么样，可以提供竞品截图或简单的 ASCII/线框草图让 AI 理解意图。

### 4. AI交互：Vibe Coding 实践指南
- **提供充足上下文（Context）**：利用现有的代码库、PRD 文档、数据库结构或成熟框架的官方文档作为 AI 的上下文。
- **分步喂上下文，切忌“一口吃成胖子”**：
  - **第一步（脚手架与数据）**：扔入 PRD 和数据表设计，让 AI 生成数据库 Schema、ORM 配置和核心实体类型。人工 Review 数据结构。
  - **第二步（后端逻辑）**：让 AI 生成 Service 逻辑、API 路由或 Server Actions。
  - **第三步（前端与联调）**：在后端骨架清晰后，提供 UI/UX 设定，让 AI 生成具体的前端组件并对接接口。
- **教学式交互**：面对不熟悉领域的代码或错误，要求 AI “先解释原因，再给出修复方案”，而不是盲目 Copy-Paste。

### 5. 验收与迭代：
- **小步快跑，单点验收**：每个小功能生成后立即测试，不要等生成了上千行代码再去运行。
- **审查“幻觉”与“弃用 API”**：重点检查 AI 是否引入了未要求的三方依赖，或者使用了旧版框架的语法（如 React 15 时代的写法）。
- **细粒度版本控制**：利用 Git 进行高频率的原子提交（Atomic Commits），有问题随时回滚。

# 项目实践：个人灵感与需求治理系统

## 1. 核心概念
系统分为两大核心模块，承载不同的信息生命周期：
- **看板（Kanban）**：**流动的**，负责需求的推进和流转。
- **知识库（Knowledge Base）**：**沉淀的**，负责经验的积累和长期查阅。

## 2. 状态流转流程 (看板模块)
Idea → PRD → Implement → Verify → CI/CD

### 各阶段准入/准出条件
| 阶段 | 准入条件 | 准出/流转条件 | 核心动作 |
|------|----------|----------|---------|
| **Idea** | 捕捉到痛点或痒点，存在 Inbox 中 | 描述清楚具体的场景和期望结果 | 快速记录，不求完美 |
| **PRD** | 决定将 Idea 转化为实际需求 | JTBD 格式完整，验收标准明确，DoD 清晰 | **利用 AI 辅助**填充完善需求细节和模板 |
| **Implement** | PRD 已通过人工评审 | 功能可运行，代码符合规范，自测通过 | **Vibe Coding** 生成与调试代码 |
| **Verify** | 在本地或测试环境可演示 | 边界测试通过，满足 DoD | 自身体验与用户验证 |
| **CI/CD** | Verify 通过 | 自动化部署到生产环境，打上版本 Tag | 自动化构建与发布 |

### Verify 阶段详解
- **自测**：开发者自行验证主体功能与异常边界。
- **用户验证**：真实用户环境试用并收集反馈。
- **迭代修正**：根据反馈将 Bug 或优化点重新投入 Inbox 或对应 Kanban 阶段。

## 3. 功能需求分析 (诊断与收敛)

### 3.1 核心痛点与 Must-Have 功能
1. **时间碎片化导致的高频上下文切换**
   - **解决方案**：极速录入的 **Inbox（收集箱）**。
   - **场景**：下班路上有灵感，一键速记；工作时有突发想法，记录后继续原工作不被打断。
2. **需求简短且缺乏执行细节**
   - **解决方案**：**需求“养殖”空间（看板系统）**。
   - **场景**：将简短的 Idea 拖拽入 PRD 列，系统提供标准 PRD 模板，或直接调用 AI 根据一句话自动扩写完整 PRD。
3. **技术与经验碎片化难以复用**
   - **解决方案**：**经验沉淀所（知识库系统）**。
   - **场景**：遇到好文章、工具或踩坑记录，统一归档。建立专门的 `Vibe Coding 规范与技巧` 目录，不断迭代方法论。支持与本地 Markdown（如 Typora）双向联动。
4. **多渠道信息散落**
   - **解决方案**：**统一聚合（集成 Inbox）**。
   - **场景**：支持 RSS 订阅拉取、Telegram/WeChat Bot 消息转发收集、以及自动化任务的结果回调。

### 3.2 痒点与 Nice-to-have 功能 (未来迭代)
- **AI 深度介入**：
  - 自动为 Inbox 里的零散想法打标签、分类。
  - 根据多个相关 Idea 自动合成一个大的 Epic（史诗需求）。
- **Git + CI/CD 联动**：将 Kanban 状态与 GitHub/GitLab Issue 状态双向同步，提交代码自动扭转状态。
- **多用户协作**：支持团队版，任务分配。

## 4. 复盘与进化机制
系统需要内置轻量级“复盘”机制，每个需求卡片跑通 `CI/CD` 归档后：
1. **经验沉淀**：本次开发中哪些代码/方案做得好？（提取复用经验 → 存入知识库）。
2. **方法论调整**：本次 Vibe Coding 过程中踩了什么坑？AI 提示词有什么可优化的？（更新方法论）。
3. **衍生需求**：新发现的痛点是什么？（生成新的 Idea → 进入诊断期 Inbox）。

# Vibe Coding 实施指引（Next Steps）

针对当前这个“个人灵感与需求治理系统”，下一步我们将采取以下实际工作流：

1. **确定技术选型**：明确具体使用什么前端、后端、数据库。
2. **第一步：数据模型设计（Schema 生成）**：利用 AI 抽象出 `Idea`, `KanbanTask`, `KnowledgeDoc` 等实体结构，并在本地跑通数据库。
3. **第二步：MVP 界面搭建（Inbox 与 看板）**：借助 AI 生成前端基础页面布局和拖拽组件。
4. **第三步：功能联调与 AI 流程打通**：连接前后端，并在系统中实现“利用 AI 自动将 Idea 扩写为 PRD”的特色化功能。
5. **第四步：知识库集成**：实现文档的增删改查及层级管理功能。
